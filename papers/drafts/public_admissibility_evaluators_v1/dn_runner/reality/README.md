# Reality-mode ΔN runner, 2026-10-03
Prereg `PREREG.md` (commit b536031 before code; Amendment 1 committed at 77147be before the second run). Runner `dn_reality.js`, systems `systems/s1..s6`, `selftest_reality.js` -> `out_selftest_reality.json`. Node 20+, stdlib only. Usage: `node dn_reality.js <target.js>`.
What differs from the first runner: the runner serves the authoritative registry and the effect sink over HTTP and observes effects at the sink (acceptance, status and revision at receipt are the sink's own records). The target only triggers one action. A system that never consults the registry is caught by reality (flag REALITY_NOT_CONSULTED; its effect lands while the registry says not standing). The first runner's adapters wired themselves to the world and reported effects; that is no longer possible here.

## What it means, and does not
- Tb in reality mode is "immediately after the last registry read". For an effect on an external system it is closable only if the effect boundary checks a fence the system carries (the sink offers one, the standard remedy). A system that does not carry the fence fails at that timing: this grades whether the deployment uses the boundary's check, not the system's decision logic alone. The fence policy is part of the printed scope.
- The sink does not judge status or vocabulary. Vocabulary handling is graded by what the system does with a status word reality serves.
- The system under test must be pointable at the registry URL and its effect must reach the sink. A system whose authority source and effect cannot be redirected cannot be run in this mode; a driver on its real store and an observer on its real effect would be needed, and that is the part only its owner can supply.
- Event-driven, not raced. Same-source: author, runner and the six systems are one pipeline; discrimination on known systems is the only validity shown. A conforming result is relative to the declared forms, timings and fence policy.
